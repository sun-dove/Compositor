# Compositor Windows 中文版：迁移与上游同步设计

状态：负责人已在会话中确认，Windows 基础实现及本地验收已完成；远端发布和实测版本记录见《交付与验收》。原设计中的后续能力仍按新场景逐项适配。
票据：COMP-WIN-ZH-001。日期：2026-10-09。

## 一、背景与目标

用户已 fork `sun-dove/Compositor`，希望制作 Windows 中文图像编辑软件，并长期跟随原作者更新。

检查基线：fork 的 `main`，提交 `22c7b8d5b23bb1e27a5746912061b23757c4f554`。上游为 `robbietilton/Compositor`。

已核实的事实：

- README 要求 macOS 26、Apple 芯片和 Xcode 26；没有 Windows 构建步骤。
- 软件采用 SwiftUI/AppKit；画布采用 Metal/Core Image/Core Graphics，部分智能功能采用 Vision。Swift 支持 Windows 不代表这些 Apple 框架支持 Windows。
- 仓库中有少量 C 像素算法，可逐个核实移植条件；不能据此认定全部核心可直接复用。
- 作者明确表示暂不接受翻译 PR。中文化应在自己的实现中维护。
- `.comp` 是含 `manifest.json` 和 `images/` PNG 的目录包。当前写入格式版本为 11，Mac 原代码接受版本 1–11；Windows 初版支持范围需要单独定义，不能直接承诺全兼容。
- 原软件使用 Sparkle 更新 Mac 安装包，不能用于向 Windows 用户分发原作者的 Mac 安装包。
- 许可证为 MIT，允许修改和分发，但必须保留版权声明及许可证；新增依赖另行核查许可。

目标：保留 Mac 原工程，新建 Windows 中文实现，以文件协议、算法语义和验收用例连接两端。上游同步分为源代码同步与功能迁移；用户端软件更新是另一条发布流程。

## 二、方案比较

| 方案 | 实施方式 | 跟随上游的成本 | 结论 |
| --- | --- | --- | --- |
| A：现有 Swift 工程增加 Windows 条件分支 | 保留 Swift 语言，重做 Windows UI、渲染和系统 API，尝试共享无平台依赖部分 | 原代码大量耦合 Apple 类型，条件分支会持续扩大；不能靠更换编译目标完成 | 暂不推荐；先做深入解耦评估才可能实施 |
| B：同一 fork 中新增 .NET + Avalonia + SkiaSharp 实现 | 新增桌面界面、文档模型、文件读写和画布；按需桥接可移植 C 算法 | 上游提交可持续合并，Windows 功能逐项迁移，需要持续维护差异表 | 推荐作为 Windows 优先的起点，具体版本待实现前核实 |
| C：新增 Tauri + Web UI + Rust/WebGPU 实现 | Web 技术实现界面，Rust 处理文件与计算，画布另做 | 也需要迁移核心；浏览器输入、显存、WebView2 和画布性能需额外验证 | 有成熟 Web 技术积累时可选 |

推荐 B 的原因：符合本机 Windows 桌面使用目标；界面本地化、中文输入和系统文件对话框有现成基础；新代码能放在独立目录中，减少触碰现有 Mac 路径。SkiaSharp 不会自动替代所有 Metal/Core Image 功能，复杂混合、滤镜和性能仍需逐项实现与验收。

Jev 辅助判断：已通过本机 PowerShell 请求 TypeSafe 接口，返回模型 `jev-1.13.0`。迁移性质选择“保留 Mac 工程，新增 Windows 实现”，概率 1.0、confidence 1.0。这个结果仅辅助界定范围，不是编译、性能或产品验收证据，也没有替代方案 B 的技术评估。用户指定的 `jev.ps1` 路径不存在，实际按 Jev 技能通过进程环境中的密钥直接调用；未保存或输出密钥。

## 三、接口与数据结构设计

建议新增目录，确认后再创建：

```text
windows/                 Windows 桌面应用与平台适配
windows/core/            文档、编辑命令、历史、图层与文件协议
windows/resources/      zh-CN / en-US 资源
compatibility/          正式的跨端黄金样例与契约资料
docs/windows/           中文设计、票据、同步记录与能力差异表
```

以上仅为草案，不是已经创建的模块。

新增接口概念：

- `IProjectReader.Read(path)`：返回文档与能力报告，或结构化错误；读取失败不替换当前文档。
- `IProjectWriter.Save(document, path)`：先完成独立暂存和验证，再执行可恢复的替换；保存失败保留原项目。Windows 目录替换的具体策略必须独立验证，不能假设与 macOS 文件协调器等价。
- `IRenderer.Render(document, viewport)`：画布与导出共享图层语义；明确 sRGB、预乘 alpha、坐标方向与采样方式。
- `IEditCommand.Execute/Undo`：一次用户操作对应一次可撤销编辑；取消导入不产生半完成文档。
- `ILocalizer.Get(key, arguments)`：中文资源优先，缺失键回退英文；不翻译序列化值。

新增数据契约：

- `ProjectReadResult`：文档、源格式版本、兼容性问题列表、是否允许编辑和保存。
- `CompatibilityIssue`：稳定代码、受影响图层、严重程度、用户可采取的操作。
- `OperationError`：稳定错误代码、可重试标记、中文资源键、必要参数。
- 主要错误代码：`InvalidManifest`、`UnsupportedVersion`、`UnsupportedFeature`、`MissingAsset`、`UnsafePath`、`DocumentTooLarge`、`AccessDenied`、`SaveFailed`。

初版仅允许编辑明确支持的项目子集。遇到不支持的调整层、混合模式、文字或效果，默认拒绝编辑并显示清单；不得静默忽略后继续覆盖原文件。需要只读预览时作为单独场景设计，不能假设 PNG 兜底足以呈现所有调整层。

中文界面可以显示“正片叠底”，manifest 中仍写上游规定的 `Multiply`。中文菜单不等于中文文字工具：中文输入法、字体、换行与 UTF-16 文本区间要单独验收。

保持既有公开接口、返回类型、字段默认行为与生产路径不变。新增字段一律可选，Windows 专用偏好放在应用配置中，不随意扩展 `.comp`。如必须修改既有代码，另开票据说明原因、列出全部调用方、回滚方案，取得负责人确认后再改。

## 四、上游同步与软件发布

本机已克隆 fork，并配置：`origin` 指向用户 fork，`upstream` 指向原作者。没有推送、修改 GitHub 设置或开启定时任务。

建议分支约定：

- `main`：尽可能保持纯净的上游镜像；首次设置前先核对是否已有用户独立提交。
- `windows-zh`：Windows 中文产品开发分支，定期合并镜像分支。
- `sync/*`：每次升级的临时审查分支；门通过后才合并到产品分支。

每次同步执行：抓取上游提交 → 对比源码、协议、C 算法和测试变化 → 更新中文能力差异表 → 对已有能力执行回归门 → 将新增能力写成场景及红门 → 单独迁移 → 通过后发布。

需要强调：`git merge` 可以带来作者的源码，但不会把新 SwiftUI 控件或 Metal 功能自动变成 Windows 功能。“跟随作者”应理解为持续评估和迁移，不承诺同日或自动全量功能对齐。

后续可新增工作流自动检查上游、形成待审查同步 PR；冲突、兼容性差异或门失败时必须停在审查阶段。不要仅靠 GitHub 的 Sync fork 按钮管理产品分支。定时任务和远端工作流须在设计确认后的实施范围内创建。

Windows 用户端更新使用自己的版本号、Windows 安装产物和更新清单。初版可通过自己的 Releases 手动下载；自动安装更新需要另行设计签名验证、失败恢复及不干扰未保存文档的体验。上游 Mac 更新地址不作为 Windows 更新源。

## 五、按真实场景定义验收门

下面是待实现的门规格，尚未编写执行程序，未宣称已红或已绿。设计确认后，先编写并运行对应门，确认新增能力门为红，再实现。正式验收代码和黄金样例须明确登记为长期交付物；其余临时样例、缓存和日志按用户规则清理。

| 场景 | 体验门先定义 | 倒推出的功能门 | 执行方式 |
| --- | --- | --- | --- |
| S01 Windows 中文启动 | Windows 上打开窗口，菜单和错误提示中文；空文档保存按钮禁用 | 应用可启动，语言资源可解析，空文档命令状态正确 | Windows 构建启动验证与 UI 自动化；声明实际测过的系统版本、架构 |
| S02 导入照片后合成 | 导入 PNG/JPEG，可缩放画布、移动图层、调整可见性/透明度，导出透明 PNG；Ctrl+Z/Y 工作 | 图层顺序、变换、预乘 alpha、历史和导出尺寸符合黄金结果 | 全部登记黄金用例与完整 UI 编辑流程；像素误差边界在实现前固定 |
| S03 中文路径与安全保存 | 在含中文路径中保存，重开后图层一致；保存失败给出中文错误且文档仍可操作 | `.comp` 子集往返无损，原项目在注入写入失败后仍有效 | 确定性文件往返门、失败注入、中文路径 UI 流程 |
| S04 不兼容项目 | 明确显示缺失资源、损坏元数据、过新版本、未支持功能；当前文档不变，禁止覆盖 | 错误分类可区分，兼容报告完整，失败不替换当前状态 | 每类错误均执行确定性门及对应 UI 门，不抽样省略 |
| S05 跨端已支持项目 | 作者 Mac 版与 Windows 版打开支持子集后结构一致，合成结果达标 | 序列化字段、默认值、图层顺序及像素语义一致 | Mac 基线生成黄金产物，Windows 全量比较；没有 Mac 验证环境则明确列为未完成 |
| S06 作者发布新版本 | 维护者可看到同步提交范围、待迁移能力和失败原因；同步不会静默发布 | 基线可追溯，旧门不退化，冲突或失败阻断合并 | 提交对比记录、完整兼容门与工作流阻断验证 |
| S07 中文文字工具（新增能力时才开工） | 拼音输入、选字、换行、保存重开均正常；缺字体有可理解的提示 | 中文输入状态、文字布局、字体策略和 UTF-16 区间一致 | 输入法 UI 门、文本序列化门、字体及跨端显示对比 |

所有确定性门不调用大模型，应在对应平台 CI 必跑。若之后加入 Agent 自动编辑项目能力，再新增按产物判定的任务评测门；不能以 Jev 判断或代码覆盖率代替功能验收。

## 六、实施顺序与确认项

1. 负责人确认目标与方案；默认目标为 Windows 桌面软件、简体中文优先。
2. 确认 Windows 支持版本、CPU 架构、首版文件格式子集，以及正式保留的验收资产范围。
3. 针对 S01–S04 固定体验、契约、黄金结果和错误分类；先运行门并记录未实现的红门。
4. 新增 Windows 工程与中文资源，实现导入、基础图层编辑、撤销、PNG 导出及安全保存。
5. 在真实 Windows 上使 S01–S04 变绿；在可用 Mac 环境中完成 S05。若缺 Mac 环境，不宣称跨端全面验证。
6. 建立 S06 对应的源码同步审查流程，记录每次上游基线；再按新增场景引入其他编辑能力。
7. 达到已确认首版的全部门后，生成 Windows 安装产物；签名、发布、自动更新另按确认范围实施。

建议首版闭环：中文启动 → 导入图片 → 基础多图层合成 → 撤销 → 导出 PNG → 安全保存并重开受支持的 `.comp`。不要同时承诺完整 PSD/PSB、所有滤镜、RAW、抠图与 Mac 全功能对齐。

设计确认后的实施进展见《交付与验收》。设计阶段记录保留为方案背景，不能作为最新运行状态。

实施采用新增文件，不改变原版 Mac 文件。源码工作副本作为维护交付保留；正式验收程序已登记，临时运行样例按精确路径清理。
