# Compositor：GitHub 自动同步、自动打包与客户端更新设计

日期：2026-10-09。票据：COMP-WIN-ZH-002。
状态：根据用户明确目标修订的设计草案，尚未实施。

本设计取代上一份设计中“先手动发布，后续再设计自动更新”的安排：自动同步、打包、发布、客户端更新均属于首版目标。平台迁移分析及向后兼容要求继续有效。按用户“设计先行”规则，确认本设计后再编码。

## 一、用户最终要看到的结果

作者提交代码 → GitHub 自动同步 → 自动构建 Windows 中文版 → 验收通过 → 自动发布自己的版本 → 本地软件启动后检测更新 → 下载校验 → 保存工作并退出 → 安装新版本并重启。

正常情况下无须维护者手动打包、上传安装包或维护版本地址。不能同步、不能构建、未通过验收或不能安装时，保留最后一个可用版本，并给出对应原因。

自动化的边界：现有仓库只有 Swift/macOS 工程，自动同步不能把 SwiftUI/AppKit/Metal 转为 Windows 功能。必须先有可构建的 Windows 中文实现。后续已适配范围可以自动回归和发布；上游新增的平台专用能力仍需迁移。不把无人监督的 AI 改写作为每次发布的必要步骤。

## 二、两种自动同步方案

| 方案 | 触发方式 | 优点 | 代价 |
| --- | --- | --- | --- |
| A：定时检查上游 main | 建议每小时检查；只在基线变化时进入同步与构建 | 跟随源码提交，满足“同步完自动打包” | 上游开发中提交可能构建失败；频繁发布需要去重与合并触发 |
| B：定时检查上游正式 Release | 新正式版本才同步对应 tag 并构建 | 较稳定、发布频率较低 | 不能跟随每次源码提交 |

推荐 A，按用户要求同步代码；默认 stable 频道只发布全部已确认门通过的构建。需要更严格稳定性时切换 B，无须更换客户端协议。GitHub schedule 不保证精确整点运行，因此不能承诺作者提交后立即更新。

采用同一 GitHub Actions 工作流协调同步、构建、验收和发布，避免依赖“GITHUB_TOKEN 推送代码后再次触发 push 工作流”的错误假设。自动合入后的代码由后续 job 显式检出固定 SHA；手动触发用于失败恢复。fork 首次使用时需启用 Actions，schedule 所在分支必须为默认分支。

## 三、仓库与流水线设计

角色分离：

- `upstream-mirror`：记录作者原始源码基线，保持镜像角色。
- `windows-zh`：产品分支，包含新增 Windows 实现、中文资源及自动工作流，建议设为用户 fork 的默认分支。
- 单次运行保存上游 SHA、产品候选 SHA、最终发布 SHA；同步过程在临时候选状态执行，不直接覆盖已发布分支。

不要对产品分支使用 force push、reset 或“无条件覆盖为上游”。上游修改到本地同名文件时，出现合并冲突就停止自动发布；维护者解决一次后自动链路继续。

单次工作流：

1. 在固定上游仓库中读取 main SHA；与上一次成功处理的 SHA 比较。未变化则退出，不重复发布。
2. 在临候选分支合并上游；产生同步冲突则记录失败，保留产品分支和当前 Release。
3. 检出候选 SHA，构建 Windows 中文应用，运行所有既有确定性门与体验门。
4. 检查 `.comp` 格式、已支持能力与更新协议。若上游越过已实现的兼容边界，阻断 stable 发布；保持“同步源码成功”与“Windows 功能迁移完成”两个独立状态。
5. 验收通过后打包，检查安装产物，签署更新元数据及产物，验证签名；最终包通过安装升级门后才允许进入发布。
6. 校验产品分支未被其他运行推进后，以正常推送合入候选；并发变化则重新运行，不强推。
7. 创建自己的 GitHub Release 草稿，上传对应 Windows 架构的安装包、更新包与元数据；校验远端资产可下载后再公开。
8. stable 更新索引最后指向完整新版本。该步骤失败则客户端继续收到旧索引；重试按固定发布身份幂等完成。

应区分“最后检查到”“最后合入”“最后成功发布”三个基线，避免一次构建失败导致后续检查把版本误当成已完成。安装包和更新包必须对应同一产品 SHA。

并发与权限：同一产品频道串行发布，不在发布中途取消旧运行；PR 验证使用只读权限，发布 job 最小化授予 contents 写入权限。签名凭据保存在 GitHub Secrets 或适用的签名服务中，不写进仓库。上游新提交不得无审查替换自有发布工作流；若涉及发布脚本、CI 或签名路径，停止自动发布等待处理。

## 四、Windows 打包与更新方案

保持前一设计推荐：新增 .NET + Avalonia + SkiaSharp 的 Windows 实现。

| 更新方式 | 说明 | 选择 |
| --- | --- | --- |
| 成熟 Windows 更新框架 | 候选 Velopack；需实现前核实当前 API、许可、签名验证能力、安装升级和失败恢复行为 | 推荐优先评估，不把未核实的能力当成框架现成功能 |
| 自研安装与替换器 | 自己处理应用锁、安装目录、包验证、退出重启、失败恢复 | 维护工作更大，成熟框架不满足门时才选 |

客户端 updater 以新增接口封装，不改变作者现有 Sparkle 路径。默认按用户级安装考虑，减少每次升级需要管理员权限的情况；支持系统级安装时另开场景门。

客户端启动完成后异步检查自己的 stable 索引，不阻塞打开项目。索引中的版本高于已安装版本且系统/架构匹配时，显示中文更新提示。可后台下载，安装前要求文档已保存且编辑进程退出；保存失败或用户取消时继续使用当前版。

更新包必须完整下载到独立暂存位置，核实大小、哈希及可信数字签名后才安装。只验 SHA-256 不等同于验证来源：元数据或包需由可信签名绑定，客户端内置相应公钥。更新元数据签名与 Windows 安装程序代码签名是两种不同用途；实现前决定具体工具和验收方式。

在国内访问 GitHub 不稳定时，客户端显示“暂时无法检查更新”或“下载中断，可重试”，不能显示成“已是最新版”。首版更新源为用户自己的 GitHub Release；如实测网络影响体验，可在保持签名验证的前提下新增自有分发镜像。不会承诺所有网络环境下无条件顺利更新。

## 五、新增接口与契约

- `IUpstreamSync.Run()`：返回检查到的基线、候选 SHA、冲突和状态。
- `IReleasePublisher.Publish(candidate)`：返回 Release 身份、完整资产清单及索引发布状态；相同候选重复执行不创建重复正式版本。
- `IUpdateService.CheckAsync()`：返回 `UpToDate`、`Available`、`NetworkUnavailable`、`InvalidMetadata` 或 `IncompatibleSystem`。
- `IUpdateService.DownloadAsync(release)`：返回暂存包或 `DownloadFailed`、`IntegrityFailed`、`SignatureFailed`、`InsufficientDiskSpace`。
- `IUpdateInstaller.ApplyAsync(package)`：只允许在已保存、退出条件满足时调用；返回完成或可恢复安装失败。

新增发布记录：`productVersion`、`releaseSequence`、`upstreamCommit`、`productCommit`、`channel`、`minimumOs`、`supportedArchitectures`、`projectFormatCapability`。

新增更新元数据：`schemaVersion`、版本身份、每架构资产的 URL/字节数/哈希、签名信息、中文更新说明、最低系统及更新器要求。元数据签名覆盖规范化的完整有效载荷；具体序列化和签名算法确认后固定。

产品版本独立递增，例如 `0.1.0`、`0.1.1`；显示关联上游版本/提交但不照抄上游版本作为唯一更新序号。不能用提交时间或 tag 字典序替代版本比较。未来变更更新协议必须保留旧客户端可读取的入口。

## 六、验收门：先体验，再功能

以下是已确认的门规格。各门的实测结果与未执行范围必须以《交付与验收》为准，不把设计规格当作通过证明。正式验收程序保留，临时运行产物按精确路径清理。

| 真实场景 | 体验门 | 功能门与执行方法 |
| --- | --- | --- |
| 作者有新提交且可兼容 | 维护者无需操作即可得到对应 Windows 发布；本地旧版可发现它 | 用固定上游提交与受控仓库跑完整同步/构建/发布链；核对候选、包、索引三者 SHA 一致 |
| 上游没有变化 | 不重复下载、不重复发布 | 连续执行检查，版本及正式资产不增加 |
| 同步冲突或构建/回归失败 | 维护者看到明确失败类别；普通用户仍使用上次可用版本 | 对各类失败逐一注入，核对 stable 索引未推进、产品分支无覆盖 |
| 新上游格式超出 Windows 支持范围 | 显示能力差异，阻断错误版本自动上线 | 格式/能力契约门失败必须阻断正式发布，不能只检查编译成功 |
| 上传中途失败或重复运行 | 客户端不收到半上传版本，维护者可重试 | 注入上传和索引发布失败；验证公开索引只引用完整资产，重试幂等 |
| 本地旧版启动 | 中文提示新版本、说明及大小，可立即或稍后安装 | 用本地受控更新源，完整验证旧版到新版；不能只测试版本比较函数 |
| 网络断开、坏包或磁盘不足 | 显示各自中文原因，可重试或继续旧版 | 每种错误均覆盖状态、按钮可用性和安装阻断，校验失败绝不执行包 |
| 尚有未保存项目 | 提示保存后更新；取消或保存失败保持当前文档 | UI 自动化及状态门证明没有静默退出、丢失文档或覆盖未保存状态 |
| 更新安装失败 | 保留或恢复旧版，说明失败且能再次启动 | 在实际 Windows 虚拟机/测试用户环境注入替换失败，验证恢复能力及项目完整性 |
| 第一个版本安装后升级 | 初次安装版能发现后续版本，升级后可再次发现下一个版本 | 至少三个递增构建连续升级验证；覆盖中文路径、实际目标系统及架构 |

确定性门不使用大模型。已登记用例全部执行，不默默截断或以覆盖率代替发布可用性。此次为自动化流程与确定性更新状态设计，继续沿用上一轮真实 Jev 迁移范围结果，无需再次让模型决定权限、版本比较或包校验。

## 七、实施步骤与当前状态

1. 确认本设计，把完整自动链路列为首版交付，而非后续选做。
2. 明确 Windows 初版架构/系统、可编辑能力及现有用户基线，准备正式验收门。
3. 完成可构建的 Windows 中文软件；并行在同一次开发范围内实现客户端更新接口和打包验证。
4. 在受控仓库与 Windows 环境使上述更新门变绿。
5. 添加自有 GitHub Actions，设置默认分支、工作流权限和发布凭据；首次安装包内置自己的更新入口。
6. 推出连续三个构建完成端到端升级验收，再启用无人值守 stable 发布。

如任何一步必须修改正在运行的既有路径，先补充票据理由、全部调用方及回滚方案，得到负责人确认后修改。

负责人已确认本设计并授权实施。采用现有默认分支 main 保留 Mac 工程并新增 Windows 代码；上游基线由 windows/upstream-state.json 记录，产品候选仍独立验证，不进行强推。具体发布与验收结果见《交付与验收》。
